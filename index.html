LLM Systems Principles

Human reference and LLM-facing directives

01

Request Batching

Description

Request batching groups multiple processing units into bounded API requests. The goal is to reduce unnecessary API calls without creating requests that are too large, difficult to validate, or harmful to model performance.

Requirements

Batch as many compatible items as is practical while enforcing limits such as item count, serialized input size, context-window size, expected output size, and validation constraints.

Example

Instead of sending 20 paragraphs through 20 separate API calls, send the 20 paragraphs together when they fit safely within the request limits and can still be validated individually.

Directive

When multiple compatible processing units require the same inference operation, group them into the largest appropriate bounded requests. Respect model, context-window, serialized-input, expected-output, and validation constraints. Do not increase batch size when doing so would degrade task performance or make individual outputs difficult to validate.

02

Dry-Run Execution

Description

A dry run exercises the pipeline without making consequential API calls. It lets the user inspect what would happen before spending money or creating external side effects.

Requirements

A dry run should resolve and display the planned model, processing scope, request count, important parameters, resource estimates, and output destination while preventing live API execution. 

DRY RUN
No API requests will be sent.


Model
  Model:              gpt-5-nano
  Reasoning effort:   medium
  Temperature:        unspecified

Scope
  Stage:              06B
  Input:              output/stage06a.json
  Processing units:   746
  Reusable results:   700
  New items:          46

Requests
  Planned requests:   3
  Batch limit:        20 items
  Largest batch:      20 items

Estimated resources
  Input tokens:       ~72,000
  Output tokens:      ~12,000
  Total tokens:       ~84,000
  Incremental cost:   ~$0.18

Output
  Destination:        output/stage06b/
  Existing artifacts: preserved


DRY RUN COMPLETE
No API requests were sent.
Example

Running –dry-run reports that 12 requests would be sent, which model would be used, and the estimated token consumption, but sends no requests.

Directive

Provide a dry-run mode for workflows with consequential model execution. Resolve and report the planned model, processing scope, request count, relevant parameters, resource estimates, and output destination without making live API calls or creating consequential external side effects.

03

Preflight Validation and Cost Estimation

Description

Preflight checks determine whether a planned run is valid and estimate its resource requirements before execution. In resumable pipelines, the estimate should focus on work that still requires new inference.

Requirements

Before execution, identify new requests, estimate token consumption and incremental monetary cost after accounting for reusable results, and stop the run if configured operational limits would be exceeded.

Example

A preflight report might say: 

PREFLIGHT CHECK


Work
  Processing units:        746
  Reusable results:        700
  New items:                46
  Planned requests:           3

Estimated resources
  Input tokens:         ~72,000
  Output tokens:        ~12,000
  Total tokens:         ~84,000
  Incremental cost:       ~$0.18

Configured limits
  Token ceiling:         100,000
  Spending ceiling:        $1.00


PREFLIGHT PASSED
Execution is within configured limits.

If the run exceeds a configured token or spending ceiling, execution is blocked.

Directive

Before consequential execution, validate the fully resolved plan and estimate the resources required for new work. Account for reusable results when calculating planned requests, expected token consumption, and incremental cost. Block execution when configured operational limits would be exceeded.

04

Human-in-the-Loop Execution Gate

Description

An execution gate ensures that consequential API calls happen only after explicit human authorization. Safe behavior should be the default.

Requirements

Live execution must require an affirmative action, and the guard should be enforced at the consequential execution boundary where practical rather than relying only on a user-interface convention.

Example

A command requires –execute before making API calls. The API-calling function also refuses to run unless it receives an explicit execution authorization.

Directive

Require explicit human authorization before consequential API execution. Make non-execution the safe default, and enforce the authorization guard as close as practical to the boundary where the consequential call occurs rather than relying only on a user-interface convention.

05

Execution Provenance

Description

Execution provenance preserves enough information to understand, audit, and reconstruct what happened during each LLM invocation. Raw model responses are primary evidence and should not disappear when parsing fails.

Requirements

Record model identity, relevant parameters, token usage, timestamps, prompt and configuration versions, hashes or fingerprints, and request/response artifacts. Preserve the authoritative raw model response before lossy parsing, normalization, or transformation.

Example

For each call, save the raw response first and then the parsed result, together with the model snapshot, prompt hash, timestamp, token usage, and request ID.

Directive

Persist sufficient provenance to audit and reconstruct each LLM invocation. Record execution-critical inputs and metadata, including model identity, relevant parameters, prompt and configuration versions, timestamps, token usage when available, and stable fingerprints. Preserve the authoritative raw model response before lossy parsing, normalization, or downstream transformation.

06

Programmatic Output Validation

Description

LLM output should not be trusted merely because it looks plausible or satisfies a generation-time schema. Independent code should verify the properties that downstream processing depends on.

Requirements

Use generation-time constraints when useful, but independently enforce structural schemas, allowed values, logical consistency, and source-grounded invariants before accepting an output.

Example

If the model returns a quotation as supporting evidence, code verifies that the quotation is an exact substring of the source paragraph. If it is not, the output is rejected or flagged.

Directive

Treat model output as untrusted until it passes independent machine-enforceable validation. Use generation-time constraints where useful, but separately enforce required schemas, allowed values, logical consistency, and source-grounded invariants before downstream acceptance. Reject or explicitly quarantine outputs that fail validation.

07

Deterministic–Stochastic Separation

Description

LLMs are useful for tasks requiring semantic judgment, but many pipeline operations are better handled by ordinary code. Separating these responsibilities improves reproducibility, cost control, and auditability.

Requirements

Use LLM inference where model judgment is genuinely needed. Perform deterministic transformations, identifiers, calculations, joins, filtering, and other mechanically reproducible operations programmatically.

Example

Ask the LLM to identify governance relationships in text. Use R or Python, not another LLM call, to count those relationships and join them to metadata.

Directive

Use LLM inference only for work that genuinely requires semantic or probabilistic judgment. Perform deterministic transformations, identifiers, calculations, joins, filtering, counting, and other mechanically reproducible operations in ordinary code.

08

Stagewise Task Decomposition

Description

Complex LLM tasks are easier to control when divided into bounded stages. Each stage should have one clear analytical responsibility and an explicit intermediate representation.

Requirements

Give each stage a well-defined input, task, and structured output. Avoid asking one model call to solve several separable analytical problems simultaneously.

Example

Stage 06A identifies proposition spans. Stage 06B receives only the admitted propositions and structures them. The second stage does not independently decide whether a proposition exists.

Directive

Decompose complex LLM work into bounded stages with distinct analytical responsibilities. Give each stage a well-defined input, task, and explicit intermediate representation, and pass structured outputs forward. Do not ask one model call to solve separable analytical problems when they can be staged clearly.

09

Checkpointing

Description

Checkpointing saves completed work incrementally instead of waiting until the entire pipeline finishes. A late failure therefore does not erase earlier successful work.

Requirements

Persist validated outputs durably at meaningful processing-unit boundaries as soon as those units are completed.

Example

After processing and validating each document, save its result before starting the next document.

Directive

Persist validated work incrementally at meaningful processing-unit boundaries. Do not defer all durable writes until the full routine completes when completed units can be safely preserved earlier.

10

Resumable Execution

Description

A resumable pipeline can continue after interruption without repeating successful model calls whose persisted results are still valid.

Requirements

Detect valid completed work and reuse it. When possible, reconstruct or finalize downstream state locally instead of paying for the same inference again.

Example

If processing fails on document 47 after documents 1-46 were saved successfully, the next run begins with document 47 rather than document 1.

Directive

Design interrupted workflows to continue from valid persisted work without repeating successful inference unnecessarily. Detect completed units whose results remain valid and reuse them; reconstruct or finalize downstream state locally when new inference is not required.

11

Dependency-Aware Incremental Processing

Description

The existence of an old output does not prove that it is still valid. Incremental processing determines reuse from the dependencies that produced the result.

Requirements

Track relevant inputs such as source content, prompts, configuration, model choices, schemas, and upstream artifacts. Recompute only outputs whose dependencies changed.

Example

If a prompt changes, rerun the outputs that depended on that prompt while reusing unaffected outputs.

Directive

Determine whether prior results remain reusable from the dependencies that produced them, not merely from the existence of output files. Track relevant source inputs, prompts, configuration, model choices, schemas, and upstream artifacts, and recompute only outputs affected by changed dependencies.

12

Atomic Persistence

Description

Atomic persistence prevents interrupted writes from leaving partial files that appear to be completed outputs.

Requirements

Do not mark a processing unit complete until its full validated result has been durably written. Use write patterns that prevent incomplete state from becoming authoritative.

Example

Write a result to a temporary file first. After the write succeeds, atomically rename it to the final filename.

Directive

Prevent partial or interrupted writes from appearing authoritative. Do not mark a processing unit complete until its full validated output has been durably persisted. Use an appropriate atomic or transactional write strategy for the storage system in use.

13

Artifact Immutability

Description

Completed or archival artifacts should remain trustworthy evidence of earlier runs. Later executions should not silently modify or replace them.

Requirements

Protect authoritative artifacts from overwrite and write new executions to distinct destinations when prior results must be preserved.

Example

Keep validated 2024 outputs frozen and write a new model run to a separate timestamped directory.

Directive

Protect completed or archival artifacts that serve as authoritative evidence of prior runs. Do not silently overwrite them. When preservation is required, write subsequent executions to distinct destinations or versions.

14

Failure Observability

Description

When a pipeline fails, the user should immediately understand where it stopped and what the failure means for already completed work.

Requirements

Report the failed processing unit, what work remains valid and preserved, and where a resumed execution should continue.

Example

Report: 

PIPELINE FAILED


Failure
  Stage:              Document processing
  Processing unit:    Document 47 of 100
  Error:              Invalid model response

Preserved work
  Completed units:    Documents 1–46
  Outputs preserved:  Yes
  Reprocessing needed: No

Recovery
  Resume at:          Document 47
  Previous results:   Will be reused


EXECUTION STOPPED
Documents 1–46 remain valid.
Restart will resume at document 47.
Directive

When processing fails, report enough state for the user or calling system to understand the failure and recover correctly. Identify where execution stopped, what completed work remains valid and preserved, what must be reprocessed, and the correct recovery or resume point.

15

Completion Reporting

Description

Regardless of whether a script involves LLMs, successful termination should be explicit. A script should not leave the user guessing whether it finished or where its outputs went.

Requirements

At successful termination, report completion and identify any externally visible files or other artifacts that were created, updated, or otherwise produced.

Example

Report: 

PROCESSING COMPLETE


Outputs
  Created:            outputs/results.csv


COMPLETED SUCCESSFULLY
1 output artifact was written.
Directive

At successful termination, explicitly report completion and identify externally visible files or other artifacts that were created, updated, or otherwise produced. Do not leave successful completion or output locations implicit.

16

Explicit Function Provenance

Description

Function calls should make their provenance immediately legible. Language-native functions, functions supplied by external dependencies, and functions defined by the project should be visually distinguishable at the call site.

Requirements

In R, call functions from non-base packages with explicit namespace qualification using package::function(). In Python, prefer module-qualified calls such as pandas.read_csv() or numpy.mean() for external packages rather than importing package functions directly into the local namespace. Functions created within the project working directory must use UPPER_SNAKE_CASE() consistently wherever they are defined or called. Apply this convention when creating functions and when renaming functions as part of otherwise authorized work; do not rename existing project-defined functions solely to enforce the convention unless a project-wide naming migration is explicitly authorized. Do not rename functions supplied by external packages to satisfy the project-defined naming convention.

Example

In R: 

mean(x)
dplyr::filter(data, year >= 2020)
jsonlite::fromJSON("config.json")
VALIDATE_OUTPUT(result)
WRITE_ARTIFACT(result, path)

In Python: 

import pandas
import numpy

pandas.read_csv(path)
numpy.mean(values)
VALIDATE_OUTPUT(result)
WRITE_ARTIFACT(result, path)
Directive

Make function provenance visible at the call site. In R, call functions from non-base packages as package::function(). In Python, prefer module-qualified calls such as pandas.read_csv() or numpy.mean() for external packages rather than importing package functions directly into the local namespace. Use UPPER_SNAKE_CASE() for functions created within the project working directory. Apply this convention when creating functions and when renaming functions as part of otherwise authorized work; do not rename existing project-defined functions solely to enforce it unless a project-wide naming migration is explicitly authorized. Do not rename external-package functions to satisfy the project-defined naming convention.

17

Standardized Script Presentation

Description

R and Python scripts should follow a consistent documentation and formatting standard without changing their computational behavior. The project’s Pretty Scripts specifications provide the authoritative presentation conventions for these languages.

Requirements

After substantive implementation and validation, format R scripts according to https://github.com/ealvaradomena/my-prompts/blob/main/prompts/pretty-r-scripts.md and Python scripts according to https://github.com/ealvaradomena/my-prompts/blob/main/prompts/pretty-python-scripts.md. Treat these specifications as documentation and presentation passes, not as authorization to refactor behavior. Preserve logic, names, paths, inputs, outputs, APIs, side effects, and execution semantics unless a separate instruction explicitly authorizes substantive changes. Revalidate behavior after applying the formatting pass.

Example

A workflow first implements and validates an R script, then applies the Pretty R Scripts specification, and finally reruns the relevant validation to confirm that only documentation and presentation changed.

Directive

After substantive implementation and validation, apply https://github.com/ealvaradomena/my-prompts/blob/main/prompts/pretty-r-scripts.md to R scripts and https://github.com/ealvaradomena/my-prompts/blob/main/prompts/pretty-python-scripts.md to Python scripts. Treat these as authoritative documentation and presentation specifications, not as authorization to change computational behavior. Preserve logic, names, paths, inputs, outputs, APIs, side effects, and execution semantics unless separately instructed otherwise, and revalidate behavior after the formatting pass.

18

Explicit Script I/O Contracts

Description

Each script should state its filesystem dependencies and products at the top of the file so that its role in the project pipeline can be understood without reverse-engineering the script body.

Requirements

Inspect the project structure and relevant source files across the working directory as needed to determine each script’s runtime filesystem dependencies and products. Do not recursively inspect generated outputs, dependency environments, version-control internals, caches, archives, or unrelated files unless they are necessary to resolve the script’s I/O behavior. At the top of every applicable script, include explicit INPUT and OUTPUT sections. Under INPUT, list every file within the working directory that the script reads, loads, sources, imports as project code, or otherwise depends on at runtime. Under OUTPUT, list every file within the working directory that the script creates or overwrites. Express each entry as a path relative to the working-directory root. Resolve constructed paths when they can be determined reliably; when a path is genuinely dynamic, document the narrowest accurate relative path pattern or location rather than inventing a filename. Keep these sections synchronized whenever filesystem behavior changes.

Example

An R script might begin with: 

# INPUT
# - data/raw/articles.csv
# - config/model.yml
# - R/helpers.R
#
# OUTPUT
# - data/processed/articles_clean.rds
# - logs/cleaning-summary.json

A Python script might begin with: 

# INPUT
# - data/processed/articles_clean.rds
# - config/extraction.json
#
# OUTPUT
# - results/extractions.jsonl
# - logs/extraction-summary.json
Directive

Inspect the project structure and relevant source files across the working directory as needed to determine each script’s runtime filesystem dependencies and products. Do not recursively inspect generated outputs, dependency environments, version-control internals, caches, archives, or unrelated files unless necessary to resolve the script’s I/O behavior. At the top of every applicable script, add explicit INPUT and OUTPUT sections. Under INPUT, list every working-directory file the script reads, loads, sources, imports as project code, or otherwise depends on at runtime. Under OUTPUT, list every working-directory file the script creates or overwrites. Use paths relative to the working-directory root. Resolve constructed paths when reliable; for genuinely dynamic paths, document the narrowest accurate relative pattern or location rather than inventing a filename. Keep the contract synchronized with filesystem behavior.
